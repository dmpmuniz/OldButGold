# REPORT_SPECIFICATION.md

> **Document Status:** Draft v1.0
> **Project:** OldButGold – HDD Revival Toolkit
> **Document Type:** Report Specification
> **Priority:** Medium

---

# 1. Purpose

This document defines the official Markdown report generated by OldButGold.

The report is the permanent record of a validation session.

Every report shall follow the same structure.

The report shall contain only information collected during execution.

---

# 2. Format

OldButGold exports reports exclusively in Markdown (`.md`).

No other report formats are generated.

---

# 3. Naming Convention

Reports shall follow the format:

```text
OldButGold-YYYYMMDD-HHMMSS-<DeviceModel>.md
```

Example:

```text
OldButGold-20260703-154522-WDC_WD10EZEX.md
```

---

# 4. General Principles

The report shall:

* be human-readable;
* be deterministic;
* contain no duplicated information;
* contain no inferred information;
* contain no predictions;
* contain no guarantees.

Every reported value shall originate from actual execution.

---

# 5. Report Structure

The report shall contain the following sections in this exact order:

```text
1. Validation Summary

2. Device Identification

3. SMART Comparison

4. Validation Configuration

5. Badblocks Result

6. Filesystem Creation

7. Validation Timeline

8. Final Assessment

9. Legal Disclaimer
```

No additional sections shall be generated.

---

# 6. Validation Summary

This section provides a concise overview.

It shall include:

* validation date;
* application version;
* validation profile;
* final classification;
* overall execution result.

---

# 7. Device Identification

This section identifies the validated HDD.

Typical information includes:

* manufacturer;
* model;
* serial number;
* firmware version;
* capacity;
* logical sector size;
* physical sector size;
* connection interface;
* transport protocol.

Only information obtained directly from the device shall be reported.

---

# 8. SMART Comparison

This section compares:

* initial SMART snapshot;
* final SMART snapshot.

Only attributes that changed shall be highlighted.

Unchanged attributes may be omitted or explicitly marked as unchanged.

The report shall never speculate about future failures.

---

# 9. Validation Configuration

This section records:

* selected validation profile;
* Badblocks parameters;
* filesystem created;
* volume label;
* execution options.

These values shall reflect the actual execution.

---

# 10. Badblocks Result

This section summarizes the surface validation.

It shall include:

* execution completed or interrupted;
* number of detected bad blocks;
* execution duration.

If bad blocks are detected, the quantity shall be reported exactly.

---

# 11. Filesystem Creation

Generated only when filesystem creation succeeds.

This section records:

* partition table type;
* filesystem type;
* volume label.

No additional filesystem analysis shall be performed.

---

# 12. Validation Timeline

The report shall record the major workflow stages.

Example:

```text
Device detected

SMART snapshot collected

SMART Short completed

Badblocks completed

Filesystem created

Final SMART snapshot collected

Validation completed
```

The report is not intended to be a debug log.

---

# 13. Final Assessment

This section summarizes the validation outcome using the official OldButGold classifications.

Example classifications include:

* Gold
* Silver
* Bronze
* Failed

The assigned classification shall follow the rules defined by the project specifications.

---

# 14. Interpretation Rules

The report shall describe only what was observed.

Examples of acceptable statements:

* No bad blocks detected.
* SMART attributes remained unchanged.
* Filesystem created successfully.

Examples of prohibited statements:

* The drive is guaranteed to be reliable.
* The drive will not fail.
* The drive is safe for important data.

---

# 15. Interrupted Validations

If validation does not complete, the report shall clearly indicate:

* interrupted stage;
* interruption reason when known;
* completion status.

No final classification shall be assigned.

---

# 16. Consistency

Every report generated from identical execution shall have identical structure.

Only collected values may differ.

---

# 17. Markdown Style

Reports shall use standard Markdown.

The following elements are permitted:

* headings;
* paragraphs;
* tables;
* bullet lists;
* horizontal separators.

HTML is prohibited.

---

# 18. Legal Disclaimer

Every report shall end with the following disclaimer.

> **OldButGold performs hardware validation using industry-standard diagnostic utilities. Validation results reflect only the observed condition of the storage device during execution. No report constitutes a guarantee of future reliability, data integrity or continued operation. Storage devices may fail without prior warning. The user remains solely responsible for backup, data protection and all decisions made based on this report. Use of this software is entirely at the user's own risk.**

---

# 19. Engineering Rule

The report is an objective technical document.

It shall never contain:

* assumptions;
* recommendations not supported by collected data;
* marketing language;
* predictions;
* certainty about future hardware behavior.

Every sentence shall be supported by observed execution data.
